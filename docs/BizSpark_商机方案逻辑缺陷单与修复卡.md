# BizSpark · 商机方案逻辑缺陷单与修复卡

> 来源：真工具 `127.0.0.1:5180` 随机条件实测（资金 `$2,000–$10,000` / 全职 / 加拿大）
> **本单已并入《BizSpark_诊断收口执行方案V1.0.md》§3/§4，不再单独发；R7 已按该单 R-05 改写。**
> 结论先行：**不是打分算法坏了，是它上游三样东西坏了——成本数据是编的、同一模板没去重、用户条件没真跑。**
> 算法只是把坏数据照单全收，所以三条全是 `95% 匹配`。
> **本轮不改 UI 图、不改 HTML 基线、不改版。** 改的是数据层与引擎层。

## 2. 定位：5 个根因，分属 4 个人

### DEF-01 · 成本表是「按比例反推」，不是采购清单（D）

三项永远 **40% / 30% / 30%**：

```
市场街  3478 : 2608 : 2609  ≈  4 : 3 : 3      合计 8695
城东     242 :  182 :  181  ≈  4 : 3 : 3      合计  605
市中心   396 :  297 :  297  ≈  4 : 3 : 3      合计  990
```

这是**先生成一个"起步总额"，再乘固定比例拆成三行**的铁证。真实采购不是这么来的。
更露馅的是 **「二手梯子」标价 USD 2,608** ——名字写着二手，钱按全新算，说明 `cost_rows` 只是套了模板文字，没做语义校验。

> 这不是"算法算错了"，是**成本数据本身是编的**。引擎再准也没用。

### DEF-02 · 同一模板被复制成 3 条（C，且契约本身漏了这条）

三条 `id` 不同、`template_id` 相同，只替换了地点后缀。V2.0 里写了「同一用户上次看过的 `id` 降权」「`saturated` 不进前三」，**但没有写「同一 `template_id` 在 Top3 中最多 1 条」**——这条是我这边契约的漏项，得认，补 K-14。

结果就是：用户要「3 个能做的生意」，拿到的是「1 个生意的 3 个地址」。

### DEF-03 · 用户条件没真正约束结果（C / F）

结果页写着「按 `$2,000–$10,000`、全职投入、加拿大来算」，却给出 `605` 和 `990` 两个远低于档下限的方案。
而三条匹配度**全部 95%**，说明打分对这三条没有任何区分度，三级 tiebreak 也没起作用——它们字段本来就几乎一样，算法只能给同分。

### DEF-04 · 国家适配串台（D / F）

选的是**加拿大**，渠道里出现 **「Nextdoor 英国街区帖子」**、**Thumbtack**（美国向）。`CountryOverride` 没按 `countries[]` 正确取用，或者渠道字段没做国家过滤。

### DEF-05 · 右栏「一页纸方案」重复堆叠（B，渲染层）

图 24 / 26 / 28 右侧同一段「一张可打印的 PDF：成本表、7 步、定价……」重复 6–8 遍，多个「导出我的方案 ↓」、多个「← 回到 3 个点子」叠在一起。
这是 `v-for` 重复渲染 / 组件重复挂载，**不是算法问题**，但用户一眼就会觉得"功能没做到位"，按上一轮定的「界面零假控件」规矩一并修。

## 3. 要补进 V2.0 的硬规则（可直接粘贴为 §3.12 / K-14）

> **产品原则：趋利避害。同一门生意，工具必须给出「最省的可行起步路径」，而不是一张虚高的采购单。**

| 号 | 规则 | 验收 |
|---|---|---|
| **R1** | Top 3 中，**同一 `template_id` 最多 1 条**。三条必须是三门不同的生意 | 三条标题、说明、工具清单互不相同 |
| **R2** | `cost_rows[]` 由**唯一成本表查表**得出，逐项真实采购口径；**禁止按总额 × 固定比例反推**；同一 item 在同一国家同一时间只有一个价 | 任意两条同 item 的价格一致；删掉"4:3:3"特征 |
| **R3** | 起步成本走**最低可行路径**：先复用已有 → 二手 / 租赁 → 再买新；「二手梯子」不得按全新价计。`min_capital` = `cost_rows` 合计 = 结果页起步标签 = PDF 成本表，**四处同源** | 四处数字完全一致；无语义矛盾（二手 > 全新） |
| **R4** | 地段 / 城市差异**只允许改**：获客渠道、客单价、竞争度、合规提示；**不允许改工具采购价** | 同 template 不同地段，成本表逐项相同 |
| **R5** | 用户所选资金档必须真约束结果：结果页 lead 里写的条件 = 实际筛选条件；低于档下限的条目不进 Top 3 | lead 与 `QuizAnswers` 一致；Top3 起步额落在所选档内 |
| **R6** | 渠道严格按 `countries[]` 取 `CountryOverride`，逐条国家过滤 | 加拿大方案里 0 条英国 / 美国专属渠道 |
| **R7（已由《诊断收口执行方案 V1.0》R-05 改写）** | Top 3 必须是 **3 门不同生意**（靠 `template_id` 去重）；**分数仅后台排序、不进前台**，不再要求「分数体现差异」 | 三条标题/说明/工具清单互不相同；前台零百分比 |
| **R8** | 右栏「一页纸方案」卡片**只渲染 1 份**：1 个预览、1 个导出按钮、1 个返回按钮 | 逐屏计数 = 1 |

### 新增用例（H 写进 `qa/cases/`）

| 号 | 步骤 | 预期 |
|---|---|---|
| **T-62** | 任取 3 组不同条件各跑一次诊断，逐条比对 Top3 的 `template_id` / `cost_rows` / 渠道 / 分数 | 三条不同生意；同 item 价格唯一；四处成本同源；渠道与所选国家一致；分数不全等；无「二手 > 全新」 |
| **T-63** | 打开任一详情页，数右栏预览块 / 导出按钮 / 返回按钮 | 各 1 个；无重复堆叠 |

### 新增 CI 校验（A 落）

- **V-13**：`validate.py` 检查同 `template_id` 的条目成本表逐项一致；检查 `min_capital == sum(cost_rows)`；检查无「二手 / 租赁」类 item 价格高于同类全新基准
- **V-14**：检查每条 `first_customers[]` 的国家标签与 `countries[]` 交集非空；`validate.py` 加 `template_id` 必填与 Top3 去重

## 5. 一句话给用户交代

**工具的价值不是"给 3 条"，是"替用户把账算明白"。**
同样的活儿、同样的家伙事儿，价签却随地段乱跳，用户立刻就会觉得"还不如我自己想"。把成本表做成唯一真源、把同一门生意只留一条、把地段只用来换客源不换价签——这三件事做完，工具才比人脑灵活。
